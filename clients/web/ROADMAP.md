# Fjord Web — roadmap

**Status:** planning. Nothing is implemented yet. The design is
[`DESIGN.md`](DESIGN.md); this file is the order of work and how each piece is
known to be done. Section numbers (§) refer to `DESIGN.md` unless they say "spec".

| | |
| --- | --- |
| `done` | Implemented, tested, released. |
| `next` | Ready to start: its prerequisites are done. |
| `todo` | Not started. |
| `open` | Waits on a decision in `DESIGN.md` §19. |

Every task is one branch and one draft PR (root `CLAUDE.md`, Working conventions).
"Accepts when" is what review checks.

## Prerequisites in fjord

These change the format and the CLI, so they land in `fjord` itself, and come
before the web slices that need them.

Done as: `password` on `POST …/links` (8 to 200 characters), hashed with **Argon2id** by Node's own `crypto.argon2` (no new dependency; OWASP minimum parameters, a PHC string that carries them) and only that string stored (new `password_hash`, `failures` and `locked_until` columns on `share_link`, migration `0011`); the token alone does not open such a link (it waits ten minutes in a pending cookie and the page asks for the password, in a form that posts to a server action), and the right password gives `fjord_share=<token>.<proof>`, a keyed hash of the link and its password hash, so a hand-set cookie with the token opens nothing; tries are claimed one at a time in a single statement and each makes the next wait (a second, then five seconds doubling to a quarter of an hour after three wrong), a try that comes too soon is not checked, and a right password starts again. Not here: changing a password or expiry after the link is made (1c.7), and the management screen. | `done` |
| 1c.6 | **Anonymous names and edit mode** (§12): name before commenting or editing; edits go to the working copy. | A link editor's change appears in the next version, credited by name. Done as: a link with the `edit` role opens in the document editor after a **name** is given (1 to 40 characters, one line, kept in the browser; read-only until then); what is typed is kept as the document's **working copy** by `PUT /doc/<id>/draft` (under `/doc/<id>` so the link's cookie is sent; no session, the cookie is the credential and must be a live link of that document whose role may edit, with the password's proof if it has one; a bad cookie is a 404, a view or comment link a 403, writes from this site only); only the body is theirs, the header is put back as it is, and a document whose header cannot be read is not edited through a link; `editors` takes `{ type: "guest", link, name }` (50 at most), the owner's page names them, and **Save version** credits each by name as a `Co-authored-by:` with a `link-<n>-<hash>@users.noreply.fjord.invalid` address while the owner stays the author. Not here: a name before commenting (1d, same name), editing by a named account's edit share, live collaboration (phase 3). | `done` |
| 1c.7 | **Share management UI**: list, change role, revoke, copy link. | The owner sees and controls every share of a document. Done as: a **Sharing** panel on a document's page (notes and encrypted files have none): *People* (who it is shared with, a role to change, *Stop sharing*, *Share with* an address, answered the same whatever the address) and *Links* (each with role, active/expired/revoked, password, expiry; *Change*, *Revoke* with a confirmation; *Make a link* with a role, an optional expiry and an optional password, whose address is shown once with *Copy link*, since only a hash of the token is kept). Not here: a "shared with you" list. | `done` |

## Phase 2 — encrypted files

In outline; tasks are written when phase 1 is done.

- `fjord-core` to WASM, the rest: age encryption and the tar container in the
  browser, identities that never leave it (passphrase-protected, unlocked per
  session).
- Browse encrypted vaults (names in `plain` naming; ids in `id` naming), open,
  edit, and commit ciphertext only. Drafts of encrypted files kept encrypted.
- Rename, move and delete in encrypted vaults, and moving files in and out of
  them (encrypting or decrypting on the way); in `id` naming a rename rewrites the
  name inside the container (spec §6.4, §7.2).
- Sealed shares of encrypted documents: copy and comments encrypted with a link key
  in the `#fragment`, or a key derived from a password.
